# MigraFlow MVP 架构设计方案（V4）

## 一、项目目标

基于 **Java + LangGraph4j + OpenRewrite**，实现面向 Java 项目的自动化代码迁移系统。

优先利用现有 Recipe 完成确定性迁移，再通过 Agent 进行验证、错误诊断与长尾修复，形成完整的迁移闭环。

采用单体应用，将 OpenRewrite 作为 Java 库集成到同一 JVM，维护项目解析结果、LST 及相关分析状态，并通过 Tools 向 Agent 提供查询与受控变更能力。文中的集成层指应用内部的 Java 代码，无需独立部署。

MVP 以“一轮 Agent 对话完成迁移”为目标：用户提供项目及迁移目标后，系统构建 Workspace，再由 Agent 自主规划、执行、验证和有限修复，最后返回结果。“一轮”指一次用户发起的完整迁移过程，内部允许多次模型调用和工具调用，不要求只有一次 LLM 请求。

CLI 支持启动后持续交互，展示一次请求的结果后继续等待用户输入；每次迁移请求仍以自主完成一次规划、执行和验证为目标。

**MVP 暂不支持：** 持久化 Task / Session 业务层、多会话管理、跨会话恢复、自动生成新 Recipe、动态重新规划、多 Agent 自由协作。

## 二、技术架构

- **Java 21**：应用实现语言与编译基线，工作流与 OpenRewrite 集成代码运行于同一 JVM；目标项目的 JDK 独立配置。
- **Spring Boot 4.1.1**：以非 Web 模式提供 IoC、配置、日志、AOP 与应用生命周期管理，不启动 HTTP 服务。
- **LangGraph4j**：工作流编排、状态管理、条件分支与循环。
- **OpenRewrite**：源码解析、LST 构建、Recipe 执行、代码变换。
- **LLM**：迁移规划、智能验证、错误诊断与代码修复。
- **Maven**：MigraFlow 自身采用单模块构建，基础包为 `com.qinghuan.migraflow`，使用标准源码、资源和测试目录；细分包按实现需要创建。
- **Maven / Gradle**：目标项目构建、依赖分析与测试执行。

采用固定阶段的工作流架构，MVP 设置 Planner 与 Executor 两个 Agent。项目分析、Recipe 执行和构建测试由服务与 Tools 提供，不分别建立 Agent。state 尚未敲定，当前不预设字段、类型及传递结构。

### 接入层与迁移入口

- MVP 提供持续交互的 Java CLI，接收本地项目路径或 Git 仓库 URL 及迁移目标，展示进度与结果；Picocli 作为启动参数与命令解析的候选方案。
- 主交互循环负责读取输入、处理命令或发起迁移、显示结果，再等待下一次输入；不将迁移业务逻辑放入该循环。
- 当前实现阶段仅接收已存在的本地目录路径，支持相对或绝对路径，提供 `/exit` 退出；Git URL、迁移目标和迁移工作流后续接入。目录检查通过后调用预留的 Workspace 准备入口，该入口暂留空。
- CLI 通过 Spring 的 `CommandLineRunner` 启动交互循环，服务和 CLI Bean 采用构造函数注入；交互结束后关闭应用容器。
- CLI 只负责参数解析及输入输出，不直接实现工作区初始化或 Agent 迁移逻辑。
- 普通迁移入口协调 Workspace 准备、工作流启动、结果汇总和资源释放，暂不引入 MigrationTaskService 或任务管理系统。
- Workspace 与 Agent Workflow 独立于 CLI；未来 Web / Desktop 接入复用核心能力，MVP 暂不开发这些界面或 HTTP 接口。

### Migration Workspace（项目上下文与运行环境）

Workspace 在 Agent 启动前完成必要准备，并在迁移过程中持续更新，关联目标项目目录、解析上下文、LST、基础项目分析、工具环境及迁移产物。

MVP 采用直接修改模式：本地输入直接使用用户指定的项目目录，Tools 在该目录读取、修改和构建项目，不将项目复制到 Workspace 下的 `project/`。Git 仓库 URL 输入先克隆得到本地目标项目，再直接操作该目录，不额外建立隔离副本。Git worktree 与复制隔离模式留待后续扩展。

目标项目目录与 MigraFlow 的运行数据目录分别管理：前者保存实际源码与构建文件，后者保存 context、artifacts、logs 和临时文件；具体路径与文件格式后续确定。Workspace 是关联这些目录和内存资源的运行上下文，不要求所有内容位于同一个目录下。

初始化按以下顺序完成：

1. 定位本地目标项目或克隆 Git 仓库，记录迁移前文件基线与已有 Git 变更，确定运行数据目录。
2. 识别模块、构建工具、JDK、依赖及 Classpath，准备构建与测试环境。
3. 检查项目基线，使用 OpenRewrite 解析所需源码，建立 LST 与基础项目概况。
4. 准备 Recipe 目录、迁移资料访问及 Tools 所需上下文，工作区就绪后启动 Agent。

就绪标准以当前迁移所需能力可用为准；详细语义索引和知识检索按需补充，MVP 不要求预先建立完整 Project Graph、向量数据库或独立知识平台。准备失败时记录原因并停止，不启动迁移工作流。

项目可以包含已有的未提交改动；迁移报告须以启动时的文件内容为基线，区分本次迁移变更。MVP 不自动提交、重置或丢弃用户已有改动；失败时保留当前文件及执行记录，不自动执行全项目回滚。

Workspace 负责管理项目环境与资源，具体解析、查询、变换和命令执行由服务及 Tools 实现，不集中到一个庞大的 Workspace 类中。迁移资料和 Recipe 目录可以共享，工作区只关联所需内容。

源码变化后同步更新 LST 与分析结果；依赖或 Classpath 变化后重新处理受影响的类型信息。完整 LST 保留在当前运行的 JVM 内，不注入 LLM 上下文或工作流 checkpoint。运行结束后释放内存与进程资源，保留目标项目及迁移产物；清理仅针对 MigraFlow 创建的临时运行数据，不删除目标项目目录。

### OpenRewrite 集成与 Tools

- 在单体内部直接调用并按需封装 OpenRewrite Java API，统一维护项目解析上下文、LST 和分析结果。
- 将项目查询、现有 Recipe 执行及局部 LST 增删改能力封装为 Tools，供 Agent 按需调用。
- LST 变更通过 OpenRewrite 的 Visitor、Recipe 或模板机制完成，由内部集成代码管理变更后的树和 Diff。
- 向 Agent 返回相关源码、类型信息与分析摘要，完整 LST 由内部集成代码维护。
- 项目架构分析结合模块、依赖、源码及配置，不将 LST 等同于完整业务架构。
- 源码或依赖变化后同步更新解析上下文，避免基于过期 LST 继续操作。

当前仅确定职责与集成方向；具体服务类名、Tools 清单、接口及状态存储方案按实现需要确定。应用自身已选定 Java 21、Spring Boot 非 Web 启动与 Maven 单模块构建，并接入 Lombok、Bean Validation、Jackson JSON、Commons Lang / IO 和 Spring 测试支持；组件版本见 `pom.xml`。LLM 接入框架及迁移组件版本尚未选定。

## 三、Agent 职责与支撑能力

### 1. Planner Agent（迁移规划）

- 根据迁移目标检索现有 Recipe。
- 按需查询项目分析结果及相关源码上下文。
- 选择、配置并组合适用 Recipe。
- 确定迁移步骤及执行顺序。
- 标记暂时无法覆盖的迁移需求。

**产出：** 迁移计划，包含 Recipe 配置、执行顺序及未覆盖需求；具体数据结构后续设计。

MVP 中只生成一次计划，不支持运行中重新规划。现有 Recipe 的参数配置与组合属于规划范围，不等同于自动开发新迁移算法。

### 2. Executor Agent（执行、验证与修复）

- 按既定迁移计划调用 Tools，逐步执行现有 Recipe。
- 调用构建、测试及目标检查能力，获取实际验证结果。
- 结合 Diff、源码、LST 查询结果和迁移文档分析错误或遗漏。
- 对当前步骤进行有限次数的局部修复，每次修复后重新验证。
- 当前步骤验证通过后推进下一步，全部步骤通过后汇总迁移报告。
- 无法安全修复或达到重试上限时标记阻塞，不自动修改迁移计划。

执行、验证和诊断统一由 Executor 协调，不设置独立的 Validator、Diagnosis Agent。执行结果、验证结果和修复记录仍应分别保存，便于复现与验收；这些记录的具体结构暂不设计。

### 支撑服务与 Tools

- 项目分析能力识别模块、依赖、版本及相关源码上下文，形成项目概况。
- 迁移前通过构建与测试工具检查基线；基线失败时先记录问题并停止迁移。
- OpenRewrite 集成代码维护 LST、执行 Recipe、提供项目查询和局部变更能力。
- 构建与验收能力执行编译、测试、依赖检查及迁移目标检查，返回明确证据。
- 服务协调 LST 变更、源码写入与分析结果更新；源码直接修改后须同步重新解析。

验收以实际工具结果和迁移目标为依据，LLM 提供补充分析，不能将失败或未执行的检查判为通过。具体节点及工具划分后续确定，增加工具调用节点不等于增加 Agent。

## 四、工作流程

用户输入项目及迁移目标 → 构建 Workspace → Planner 配置、组合 Recipe 并规划步骤 → Executor 按顺序执行每个步骤 → 保存产物并输出迁移报告。

Workspace 就绪后 Planner 规划一次；Executor 在每个步骤内完成执行、验证以及必要的调试和修复，当前步骤验证通过后执行下一步。

MVP 暂不从 Executor 返回 Planner，也不在执行过程中修改计划。无法完成当前步骤时停止并记录问题；全部步骤完成后汇总结果。流程图仅在聊天中展示。

运行结束或失败时保留计划、Diff、构建测试日志、修复记录及未解决问题，并释放运行资源。保存这些产物不依赖 Task / Session 业务模型。

## 五、后续设计事项

当前先确定 Agent 分工、服务边界和迁移流程。state 的字段、类型、更新方式，以及节点间数据传递、checkpoint、缓存和恢复机制均留待后续设计。

OpenRewrite 集成代码管理项目解析上下文、LST 与分析资源；后续实现需保证解析结果与源码、依赖一致，并能重建和释放内存资源。具体类名、接口及记录结构暂不固定。

未来产品可引入类似 Session 的 Task，组织同一项目迁移过程中的多次会话与执行记录；Workspace 继续负责项目上下文和运行资源。该方向仅作为后续扩展，不在 MVP 中预先实现 Task 实体、状态机或持久化框架。

## 六、MVP 实现范围

**必须实现：**

1. CLI 接入、直接修改模式的 Workspace 初始化、Java 项目分析与现有 Recipe 检索。
2. 基于 LangGraph4j 的 Planner 与 Executor 两个 Agent，以及固定阶段和有限修复闭环。
3. 单体内 OpenRewrite Java API 集成、LST 管理及现有 Recipe 执行与 Diff 生成。
4. 编译、测试与基础智能验证。
5. Agent 通过 Tools 查询项目及执行局部修复，并进行有限次数重试。
6. 最终迁移报告及未解决问题记录。

**暂缓实现：**

- 自动生成 YAML / Java Recipe。
- 复杂项目关系图（Project Graph）。
- 运行时重新规划迁移计划。
- 多 Agent 并行协作。
- Git worktree 与复制隔离模式。
- Task / Session 业务层、多会话管理、任务队列及跨会话恢复。
- Web / Desktop 界面、HTTP 接口及复杂知识基础设施。
- 自动证明业务语义完全一致。

## 七、预期成果

MVP 最终能够通过 CLI 接收一个 Java 项目及迁移目标，直接在目标项目目录选择现有 Recipe、执行迁移、验证结果，并对剩余问题进行有限的自主修复，一次运行返回迁移结果。

最终产出包括：

- 迁移后的项目代码
- Recipe 执行记录及代码 Diff
- 构建与测试结果
- Agent 修复记录
- 未覆盖或未解决问题清单

**核心原则：确定性迁移交给 OpenRewrite，迁移决策、智能验证与长尾修复交给 Agent。**

**集成原则：接入层负责输入输出，Workspace 管理项目上下文与运行资源，Planner 组装迁移计划，Executor 完成执行、验证与修复；服务与 Tools 承担确定性操作，LangGraph4j 管理流程。**
